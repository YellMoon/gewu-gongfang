# WebSocket + HTTP降级云中继优化设计文档

## 概述

将桌面端与数据主机之间的外网通信从长轮询模式升级为WebSocket实时通信，同时保留HTTP作为降级方案，以解决当前同步延迟高（1-2分钟）、连接开销大的问题。

## 问题分析

### 当前架构问题
1. **长轮询延迟高**：主机60秒轮询一次任务，客户端再轮询结果，端到端延迟可达1-2分钟
2. **连接开销大**：即使没有任务，也需要频繁建立HTTP连接
3. **Gateway/Backend代码重复**：两套相似的云中继逻辑，维护成本高

### Gateway/Backend代码重复原因
- **Gateway**：独立部署的云端API网关，面向外部用户（小程序、桌面客户端）
- **Backend**：本地后端服务，运行在数据主机上，处理任务认领和处理
- 两者都有cloudRelay相关路由，但职责不同，代码高度重复

### 核心组件设计

#### 1. WebSocket服务器 (Gateway端)
- **位置**：`gateway/src/websocket/server.js`
- **功能**：
  - 连接管理（认证、心跳、重连）
  - 任务通知（桌面客户端任务完成时推送）
  - 状态同步（主机在线状态、任务进度）
  - 降级检测（WebSocket不可用时自动切换HTTP）

#### 2. WebSocket客户端
- **数据主机端**：`backend/src/websocket/client.js`
  - 连接云端WebSocket服务器
  - 接收任务认领通知
  - 发送任务处理状态
  - 自动重连机制

- **桌面客户端端**：`src/services/websocketClient.mjs`
  - 连接云端WebSocket服务器
  - 接收任务结果推送
  - 接收主机状态更新
  - 降级到HTTP轮询

#### 3. 共享逻辑抽象
- **位置**：`shared/cloudRelayLogic.js`
- **提取重复逻辑**：
  - 任务状态管理
  - 认证断言验证
  - 心跳机制
  - 错误处理

### 通信流程优化

#### 桌面客户端同步流程（优化后）
```
1. 桌面客户端 → WebSocket服务器：提交同步请求
2. WebSocket服务器 → Gateway：创建任务（HTTP）
3. Gateway → 数据主机WebSocket：推送新任务通知
4. 数据主机 → WebSocket服务器：认领并处理任务
5. WebSocket服务器 → 桌面客户端：推送任务结果
6. 桌面客户端：应用同步结果
```

**预计延迟**：1-3秒（当前：1-2分钟）

#### 降级流程（WebSocket不可用时）
```
1. 检测WebSocket连接失败
2. 自动切换到HTTP轮询模式
3. 使用现有HTTP API完成同步
4. 定期尝试重新建立WebSocket连接
```

### 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 企业防火墙阻止WebSocket | 连接失败 | HTTP降级机制 |
| WebSocket连接不稳定 | 消息丢失 | 消息确认+重试机制 |
| 服务器负载增加 | 性能下降 | 连接池管理+负载均衡 |
| 兼容性问题 | 旧版本无法使用 | 渐进式升级+版本检测 |

### 预期收益

- **延迟降低**：从1-2分钟降至1-3秒
- **用户体验**：实时看到同步进度和结果
- **资源效率**：减少HTTP连接开销
- **代码质量**：消除重复逻辑，降低维护成本

## 技术栈

- **WebSocket库**：`ws` (Node.js)
- **前端WebSocket**：原生WebSocket API
- **认证**：JWT + HMAC签名
- **消息格式**：JSON
- **重连策略**：指数退避 + 随机抖动
