# 未认可学生、公开申请与双手机号学生账户设计

## 状态与替代关系

- 日期：2026-07-16
- 状态：用户已确认推荐账户模型，并授权后续按本设计自主执行。
- 本设计取代 `2026-07-14-miniapp-review-experience-design.md` 中“体验码、合成管理员/学生身份、可选审核角色”的产品入口。
- 旧实现中的服务端隔离、防火墙、有界请求、会话级任务和 Word/PDF 沙箱可以复用，但必须改为真实、已验证手机号的未认可用户会话；不得继续暴露审核体验码或合成管理员身份。

## 目标

1. 每次建立新的小程序登录会话都必须由用户主动使用微信手机号授权按钮验证当前手机号。
2. 未获认可的真实用户仍可登录，但只能进入“未认可学生”体验态，不得接触真实课程、财务、学生、设备、同步或题库数据。
3. 公开申请只允许学生和老师。管理员身份不能自助申请。
4. 一个学生业务档案最多支持学生本人和唯一家长两个手机号登录；两人都是学生角色并共享同一 `student_id`。
5. 管理员审核通过后，必须先由指定本地数据主机完成权威学生/老师档案的创建或绑定，成功回传后才开放正式权限。
6. 审核成功的账号只在账号名称旁显示“会员”标记，为未来收费渠道保留独立会员数据模型，不实现任何购买、续费或价格界面。
7. 未认可用户只能查看固定、脱敏的真实物理示例题，并可在云端 Backend 隔离沙箱中体验组卷和 Word/PDF 导出；生产运行时不依赖本地 D 盘或权威题库。
8. 后台留存登录结果和已验证手机号，同时遵守目的限定、最小必要、访问控制和明确保存期限。

## 非目标

- 不建立独立家长业务角色；家长登录后的 `user_type` 仍为 `student`。
- 不允许第三个手机号加入同一学生账户。
- 不允许学生、家长或老师公开申请管理员身份。
- 不实现短信验证码、密码登录、微信以外的登录方式或手机号自助更换。
- 不实现实际支付、订阅、到期提醒、权益套餐、优惠、会员价格或营销页面。
- 不把阿里云 Backend 或 Gateway 变成学生、老师、课程或题库的最高权威业务数据库。
- 不让微信审核员看到合成管理员数据；未知手机号与普通新用户完全走同一未认可学生路径。

## 已选择的账户模型

考虑过三种方案：

1. **一个学生档案加两条认证身份（采用）**：学生和家长各自拥有手机号、微信身份、令牌和登录事件，共享一个 `student_id`。
2. **一条用户记录保存两个手机号和两个 openid（不采用）**：难以判断令牌所有者、登录事件主体和手机号冲突，且并发绑定容易覆盖身份。
3. **独立家长角色与家庭关系模型（暂不采用）**：扩展性较强，但不符合“家长仍是学生用户”的产品要求，并增加当前不需要的角色和导航。

采用方案 1。认证身份与业务主体严格分离：

```text
student 业务档案 S1
├─ 认证身份 U1：identity_kind=student，phone=学生手机号，openid=学生微信
└─ 认证身份 U2：identity_kind=parent，phone=家长手机号，openid=家长微信

U1.user_type = student
U2.user_type = student
U1.student_id = U2.student_id = S1.id
```

同一手机号全局只能属于一条认证身份；同一学生最多存在一条 `student` 身份和一条 `parent` 身份。两个身份不共享 openid、JWT、刷新会话或登录事件。

## 系统职责边界

### Backend（阿里云 `/scheduling`）

Backend 是小程序唯一的认证与申请服务，也是以下云端数据的权威来源：

- 微信 openid 与已验证手机号之间的认证绑定；
- 登录会话、登录事件和认证版本；
- 公开申请及其审核/任务状态；
- 认证身份到 `student_id`/`teacher_id` 的映射副本；
- 会员标记及其来源；
- 固定体验题、隔离体验任务和临时导出文件；
- 由小程序创建、并由指定本地数据主机轮询处理的 V2 云任务。

Backend 不是学生、老师、课程、财务或真实题库的最高权威来源。小程序所有正式、未认可和申请请求统一使用 `https://physicsedu.xyz/scheduling`，不得在 Backend 与 Gateway 之间镜像 `users`、openid、手机号、会员或申请数据，也不得由两套服务分别签发可登录小程序的令牌。

### Gateway（阿里云根域）

Gateway 保留既有健康检查、云中继兼容和其他已验证的边界能力，但不再承担正式或未认可小程序用户认证。旧 `/api/auth/review-demo`、审核体验码和合成审核角色路由返回 410；旧审核令牌失效。Gateway 不复制 Backend 的身份或申请表。

### 指定本地数据主机

本地数据主机继续是以下数据的最高权威来源：

- 学生和老师业务档案；
- 学生姓名、学生手机号、家长手机号、家长关系、学校和高一入学年份；
- 老师姓名、手机号、科目和备注；
- 课程、排课、财务、题库及其他核心教务数据。

### 小程序

小程序只负责：

- 发起微信手机号授权；
- 呈现登录结果和对应角色界面；
- 提交/查看自己的公开申请；
- 在未认可状态下呈现固定空态和隔离示例；
- 在管理员状态下审核公开申请；
- 呈现账号名称旁的真实会员标记。

所有权限必须由服务端验证，不能只靠隐藏按钮或前端路由守卫。

## 认证与会话

### 强制手机号验证

登录页只保留一个主动作：“验证手机号并登录”，使用微信 `open-type=getPhoneNumber`。每次创建新的主登录会话时，小程序同时提交：

- 本次 `wx.login` 获取的临时登录 code；
- 本次手机号授权返回的动态 phone code；
- 小程序版本和平台信息。

服务端分别向微信交换 openid 和手机号。客户端填写的手机号永远不参与身份认证。微信临时 code、phone code、access token、JWT 和完整请求体不得写入日志或数据库。

用户拒绝手机号授权时，不会产生可验证手机号，因此只在客户端显示“需要验证手机号才能登录”，不把拒绝动作伪装成包含手机号的服务端登录记录。只要服务端成功解析出手机号，无论最终结果成功、未认可、禁用还是冲突，都必须写入登录事件。

### 身份匹配顺序

1. 以微信返回的规范化手机号查找唯一认证身份。
2. 若手机号身份没有 openid，则在事务中绑定本次 openid。
3. 若该手机号已绑定其他 openid，返回 `PHONE_WECHAT_BINDING_CONFLICT`，不得自动覆盖；只能由受控管理员更换流程处理。
4. 若本次 openid 已属于另一手机号身份，返回 `OPENID_PHONE_BINDING_CONFLICT`。
5. 若手机号不存在，创建真实 `pending` 用户行，但不授予正式角色权限。

### 两类令牌

- **未认可令牌**：`token_use=unrecognized-student`，包含用户 ID、随机会话 ID、认证版本和固定体验范围，不包含手机号或 openid。
- **正式令牌**：沿用正式用户令牌类型，包含用户 ID、角色和认证版本；中间件每次从数据库重新验证账号状态及映射。

`users.login_enabled` 继续表示“是否允许正式业务登录”，不能因为未认可用户可以进入体验态就改为 1。未认可令牌的签发由独立条件控制：用户真实存在、手机号已验证、账号未被禁用、尚未获得正式权限。

账号审核、角色、手机号绑定或禁用状态变化时递增 `auth_version`，使旧令牌失效。未认可令牌永远不能在原会话中自动升级为正式能力；审核完成后必须重新验证手机号登录。

现有刷新机制只能延续同一次已验证登录会话，并继续检查 `auth_version`。它不能把未认可令牌转换成正式令牌，也不能在失效后绕过手机号授权创建新会话。

### 登录事件

Backend 新增 `miniapp_login_events`，至少包含：

- `id`
- `user_id`（无法匹配时可空）
- `phone_normalized`（微信成功解析出的真实手机号）
- `identity_kind`（已知时为 student/parent/teacher/admin/unrecognized）
- `result_code`
- `session_id`（成功签发会话时）
- `miniapp_version`
- `platform`
- `created_at`

不采集原始 IP、设备通讯录、地理位置或用户信息对象。登录事件原始手机号默认保存 180 天，之后删除事件明细或匿名化为不可逆统计；认证身份中的手机号在账号存续期间保留。只有固定超级管理员可查看登录事件，普通管理员不能批量导出。

## 公开申请数据模型

Backend 新增版本化申请表 `miniapp_role_applications`。每次提交保存一个申请修订；其中 `revision`、`payload_json` 和提交时身份快照不可修改，状态、任务、审核与时间字段按状态机更新。核心字段包括：

- `id`, `applicant_user_id`, `application_type`
- `status`, `revision`, `payload_json`
- `verified_phone_normalized`
- `student_phone_normalized`, `parent_phone_normalized`（学生申请）
- `applicant_identity_kind`
- `host_task_id`, `host_entity_id`
- `submitted_at`, `reviewed_by`, `reviewed_at`, `rejection_reason`
- `created_at`, `updated_at`

状态机：

```text
submitted ──approve──> provisioning ──host success──> approved
    │                         │
    └──reject──> rejected     ├──retryable failure──> provisioning
                              └──terminal conflict──> manual_resolution_required

rejected ──resubmit new revision──> submitted
submitted/rejected ──withdraw──> withdrawn
manual_resolution_required ──superadmin resolves──> provisioning
```

未提交的表单只保存在小程序当前会话或本地草稿，不上传后台；用户要求留存的是登录事件，而不是未提交的个人资料草稿。一个申请人同一时刻只能有一个活动申请。学生和家长分别提交同一手机号组合时，第二个活动申请只得到“已有申请”的结果，不返回另一申请人的资料。

### 学生/家长代学生申请

必填字段：

- 学生姓名；
- 学生手机号；
- 学校；
- 当前年级：高一、高二、高三或高复；
- 家长角色：爸爸或妈妈；
- 家长手机号。

可选字段沿用现有业务字段：家长姓名、家长微信、学生来源、备注。余额、机构归属、生源类型等后台字段不允许申请人填写。

校验规则：

- 学生手机号和家长手机号必须是两个不同的有效手机号；
- 本次登录验证手机号必须等于其中一个；相等于学生手机号时 `applicant_identity_kind=student`，相等于家长手机号时为 `parent`；
- 两个手机号不能已属于其他已认可业务主体或不相容的活动申请；
- 学生姓名、学校和可选文本统一去除首尾空白并限制长度；备注不得包含文件或富文本；
- 申请人不能指定 `student_id`、余额、课程、会员期限或正式权限。

当前学年以中国时区每年 9 月为边界。设当前学年起始年份为 `schoolYear`：1–8 月取当前年份减 1，9–12 月取当前年份。高一、高二、高三、高复分别反算：

```text
grade_year = schoolYear - 0 / 1 / 2 / 3
```

Backend 在提交时计算并存储 `grade_year`，本地数据主机在处理任务时用同一算法复核。权威记录以 `grade_year` 为准，`grade_current` 由统一函数按当前学年计算。

考虑到可能涉及未满十四周岁的学生，不采集出生日期。学生本人提交前必须确认已满十四周岁；未满十四周岁的申请必须由家长手机号登录并由爸爸或妈妈身份提交/确认。家长提交时记录其监护确认，不把该确认解释为平台已核验亲子关系；管理员仍需人工核对。

### 老师申请

字段只包括：

- 姓名（必填）；
- 手机号（必填且锁定为本次微信验证手机号）；
- 科目（选填，沿用现有科目数据）；
- 备注（选填）。

公开老师申请不采集课时费。申请人不能指定 `teacher_id`、管理员权限、租户、设备或数据范围。

## 管理员审核边界

“不需要单独审核员权限”解释为：

- 所有已认可的普通管理员均可查看、批准或拒绝学生/老师公开申请；
- 该能力由管理员角色固定派生，不提供单独勾选、临时授予或“审核员”角色；
- 普通管理员不能把申请人改成管理员，不能直接操作原始用户角色，不能审核设备配对，也不能查看登录事件明细；
- 固定超级管理员继续负责管理员身份、账号禁用、设备配对和认证冲突处理；
- 管理员不能修改申请人的个人信息后直接通过。资料有误时必须填写拒绝原因，由申请人修订后重新提交；
- 审核人不能审核与自己认证身份相同的申请，所有决定写入授权审计。

管理员点击“通过”只把申请变为 `provisioning`，绝不立即设置 `review_status=approved` 或 `login_enabled=1`。

## 权威主机建档与绑定任务

### 专用任务类型

Backend 使用现有 V2 云任务协议创建内部任务 `identity-provisioning`。该任务与正式小程序任务同属 `/scheduling` Backend 的云任务库，指定本地数据主机通过 `GEWU_CLOUD_BASE_URL=https://physicsedu.xyz/scheduling` 轮询同一 owner：

- 只允许服务端管理员审核流程创建，不能通过普通 `/api/cloud/tasks` 由小程序自由提交；
- 使用 `application_id + revision + request_hash` 作为幂等边界；
- 指定当前权威数据主机 `target_host_device_id`；
- 复用原子 claim、租约、claim token、`row_version` CAS、进度、失败和完成语义；
- payload 只包含经服务端验证的申请快照和审核元数据，不包含 JWT、openid 或微信临时 code。

管理员批准前，Backend 必须确认目标主机心跳声明支持本任务协议。主机离线或版本过旧时保持 `submitted` 并返回明确原因，不制造一个永久卡住的已批准账号。

### 本地主机幂等收敛

本地主机新增 provisioning receipt，按申请 ID、修订号和请求哈希唯一。重复 claim、超时重试、进程重启或重复完成回调必须返回同一个业务实体，不得创建重复学生/老师。

学生处理：

1. 同时按学生手机号和家长手机号搜索未删除学生，且检查两个字段之间的交叉占用。
2. 无匹配时创建学生，写入姓名、学生手机号、家长手机号、家长关系、学校、`grade_year` 和选填字段，并自动维护学校表。
3. 唯一匹配且姓名/手机号/关系等关键字段兼容时复用该学生，只补全空字段；不得覆盖冲突的既有数据。
4. 多条匹配、手机号交叉占用或关键字段冲突时返回 `STUDENT_PROFILE_CONFLICT`，交给超级管理员人工处理。

老师处理：

1. 按规范化手机号查找唯一未删除老师。
2. 无匹配时创建老师，`hourly_rate` 保持空，不从申请产生课时费。
3. 唯一匹配且姓名兼容时复用，只补全空的科目/备注。
4. 多条匹配或姓名冲突时返回 `TEACHER_PROFILE_CONFLICT`。

主机返回实体类型、实体 ID、receipt ID 和结果哈希。不得把整个权威业务记录复制进任务结果。

### Backend 原子启用

主机任务成功后，Backend 在一个事务中：

1. 再次验证申请仍为同一 `provisioning` 修订且任务结果匹配；
2. 学生申请查找或创建两个手机号对应的认证身份；
3. 将两条身份分别标记 `identity_kind=student/parent`，但都设置 `user_type=student` 并绑定同一 `student_id`；
4. 另一个手机号若尚未登录，只创建/保留 openid 为空的待绑定认证身份，首次验证该手机号时再绑定微信；
5. 老师申请将当前身份绑定唯一 `teacher_id` 并设置 `user_type=teacher`；
6. 创建共享会员记录；
7. 设置正式登录状态、审核信息和新的 `auth_version`；
8. 将申请标记 `approved` 并写入审计。

任何手机号已被不相容身份占用时，整个 Backend 事务回滚，不能出现“一条身份开放、另一条失败”的半成品。

若主机已完成任务但 Backend 在最终事务前崩溃，启动时和管理员申请列表读取前执行幂等 reconciler，扫描已完成的 provisioning 任务并重复上述原子收敛。任务成功证据不能因进程重启丢失。

## 会员模型

新增独立 `account_memberships`：

- `subject_type`: `student`、`teacher` 或 `user`；
- `subject_id`: 学生 ID、老师 ID 或管理员用户 ID；
- `status`: 当前使用 `active`，预留 `inactive`、`expired`；
- `source`: 当前为 `admin_approval` 或迁移来源 `existing_approval`；
- `starts_at`, `ends_at`, `created_at`, `updated_at`。

学生和家长通过同一 `student_id` 命中同一会员记录。老师按 `teacher_id` 命中；管理员按用户 ID 命中。现有已认可用户迁移为有效会员。

当前版本中，正式角色审核成功与会员创建在同一事务中完成。会员记录不是角色提升入口，也不能绕过 `review_status`、`login_enabled`、`student_id`/`teacher_id` 绑定。未来若增加付费，只能在独立版本中定义到期及功能权益，不得把当前会员标记伪装成已实现收费能力。

小程序仅在账号名称紧邻位置显示一个小型“会员”标记；首页卡片、课程、题库、导航和弹窗不重复营销会员，也不出现价格、购买、续费或权益承诺。

## 未认可学生服务端隔离

### 固定能力白名单

未认可令牌只获得：

- `experience:read`
- `profile-application:read`
- `profile-application:submit`
- `sample-questions:view`
- `sample-paper-export`

不获得：

- `business:all` 或任何真实业务读取能力；
- `question-bank:view`（该能力只表示真实题库）；
- `question-bank:edit`；
- `users:review`；
- 设备配对、桌面同步、财务导入、真实任务或权威主机写入能力。

Backend 对 `token_use=unrecognized-student` 使用明确路由白名单，并在同一服务内让所有正式业务路由显式拒绝该令牌类型。任何未列入白名单的请求都返回 403，不能回退到普通用户、合成审核身份或匿名数据。Gateway 对该令牌一律拒绝，不能成为绕过 `/scheduling` 防火墙的第二入口。

### 空业务数据

未认可界面中的课程、排课、财务、真实学生、真实老师和统计均由固定体验视图返回空集合/零状态，绝不查询 `readonly_snapshots`、`users` 业务投影、`miniapp_tasks` 或本地数据主机。前端不得缓存上一个正式账号的数据；身份切换必须先清空所有角色和租户缓存。

### 固定示例题与沙箱

固定示例题取自用户授权的本地高三物理模拟试卷，选择题号 1、2、4、11：

- 只提交人工核对后的最小题干、选项、答案、解析和必要公式；
- 第 2 题删除非必要运动员照片引用，保留可独立作答的物理陈述和答案；
- 使用稳定的体验专用 ID，明确标注“示例题（不属于正式题库）”；
- 不提交原始整卷、D 盘路径、解析缓存或其他题目；
- 生产运行时不访问 D 盘、移动硬盘题库或真实快照。

将现有会话隔离、速率限制、请求体上限、30 分钟过期和跨会话下载拒绝移入 Backend 的独立体验命名空间。Word/PDF 只包含固定示例题，产物只在 Backend 临时沙箱存在，不写业务数据库、OSS 或本地主机。正式用户的组卷仍走权威主机 V2 任务；体验任务使用独立内存/临时文件 owner、路由前缀和缓存键，不能写入或伪装为正式 `miniapp_tasks`。

## 小程序体验

### 登录页

- 删除体验码输入、管理员/学生体验选择和审核专用文案。
- 显示真实、简短的隐私告知和隐私保护指引入口。
- 唯一主按钮为“验证手机号并登录”。
- 手机号授权取消、微信交换失败、身份冲突、限流和网络失败分别显示可理解文案。

### 未认可学生壳层

- 无论申请学生还是老师，审核通过前都使用学生风格的受限导航和界面。
- 账号区显示“体验账号”，不显示会员标记。
- 固定说明：“当前为体验账号。提交真实资料并经管理员审核后，可使用相应正式功能。”
- 首页、课程表等真实业务位置显示明确空态；不能出现虚构课程、余额、成绩、收入或人数。
- 题库页显示正式题库为空，并单独展示四道“示例题”；沙箱组卷/导出按钮只操作示例题。
- 设置或首页提供“申请正式账号”，可选择学生/家长代学生或老师。

### 申请状态

必须覆盖：加载、未提交、字段无效、提交中、已提交、审核中、主机建档中、已拒绝、可修订重提、已撤回、已通过需重新登录、网络失败。

拒绝必须显示管理员填写的可操作原因。`provisioning` 状态明确说明“管理员已通过，正在由数据主机建立正式档案”，不能显示为已开通。审核完成时旧令牌失效，小程序清理缓存并回到手机号登录页。

### 管理员审核页

现有管理员用户页增加“公开申请”区域或页内标签：

- 普通管理员只能查看学生/老师申请及其必要资料，批准或拒绝；
- 超级管理员另外保留原始用户管理、管理员身份、禁用和设备配对能力；
- 学生申请清楚展示申请人是学生还是家长、两手机号的掩码/必要审核视图、学校、当前年级/入学年份和家长角色；
- 老师申请不展示或要求课时费；
- `provisioning` 展示主机、任务阶段、失败码和重试状态；
- 所有操作防重复提交并有确认提示。

### 正式角色与会员标记

- 受认可学生和家长进入相同学生界面、相同 `student_id` 数据范围；
- 受认可老师进入老师界面，现有登录策略必须正式允许 teacher；
- 管理员进入管理员界面；
- 仅在账号名称旁显示会员标记，不新增会员页面或导航入口。

## 隐私与保留

手机号、学生姓名、学校、年级、家长手机号/关系和老师资料必须在微信小程序隐私保护指引中逐项说明用途。登录前以清晰文案说明手机号用于身份识别、账号审核、双身份学生账户和安全审计；申请页说明所提交资料会传给管理员并在审核通过时写入本地权威数据主机。

保存策略：

- 登录事件原始手机号：180 天，之后删除明细或匿名化；
- 未提交草稿：仅本地当前会话或受身份隔离的本地草稿，由用户清除；
- 被拒绝/撤回申请的完整 payload：180 天后删除，保留不可逆摘要、决定、时间和审计 ID；
- 已批准申请的 Backend 完整 payload：主机建档并稳定 180 天后删除，保留实体映射、结果哈希和审计 ID；
- 权威学生/老师资料：按账号和教务档案存续需要保留，通过设置页的账号/隐私入口申请更正或删除；
- 微信临时 code、phone code、JWT、环境密钥：从不持久化。

申请人可以在 `submitted` 或 `rejected` 状态撤回；`provisioning` 后为防止跨系统半完成，不允许自行撤回，需联系管理员处理。后台展示遵循最小必要：普通管理员能看申请审核所需资料，登录事件和认证冲突只对超级管理员开放。

该处理方式以《中华人民共和国个人信息保护法》的目的限定、最小必要、公开透明、告知同意、保存期限和未满十四周岁信息保护要求为设计基线；发布前必须同步更新微信平台隐私保护指引，不能只改代码文案。

## 错误处理和恢复

### 登录错误

- `PHONE_AUTHORIZATION_REQUIRED`：未提供手机号授权；不创建会话。
- `WECHAT_PHONE_EXCHANGE_FAILED`：微信未返回手机号；不声称记录了手机号。
- `PHONE_WECHAT_BINDING_CONFLICT` / `OPENID_PHONE_BINDING_CONFLICT`：停止自动绑定并写审计。
- `ACCOUNT_DISABLED`：不签发未认可或正式令牌。
- `AUTH_RATE_LIMITED`：返回重试时间，不能降级到匿名体验。

### 申请错误

- 字段缺失、长度、手机号或年级错误返回逐字段原因；
- 两手机号相同、已被其他主体占用或存在活动申请时返回稳定错误码；
- 幂等重复提交返回原申请，不新建修订；内容不同但使用同一幂等键返回 409；
- 被拒绝后只能创建新修订，历史修订保持只读审计。

### 主机错误

- 主机离线或版本不支持：不进入 `provisioning`；
- 可重试故障：保持 `provisioning`，按任务协议重试并显示阶段；
- 学生/老师数据冲突：转为 `rejected` 或 `manual_resolution_required`，不开放账号；
- 回调丢失或进程重启：reconciler 从任务终态幂等完成；
- 任意半事务失败：Backend 不启用任何正式身份或会员。

## 安全不变量

1. 未认可身份不读取任何真实业务快照，即使客户端伪造路由或 API。
2. 未认可身份不能创建普通云任务、桌面配对或同步任务。
3. 管理员点击通过不等于正式授权；主机权威建档成功是必要条件。
4. 一个学生最多两个手机号身份，类型分别为 student 和 parent。
5. 家长身份仍为 student 角色，只通过 `identity_kind` 区分审计主体。
6. 手机号与 openid 冲突永不自动覆盖或合并。
7. 老师申请不采集课时费。
8. 旧未认可令牌不能原地获得正式权限。
9. 会员状态不能授予角色或绕过审核。
10. 示例题不来自运行时权威题库，沙箱不访问本地主机。
11. 登录事件不保存微信临时凭证或 JWT。
12. 普通管理员不能创建管理员身份或查看登录事件。

## 测试与验证

实施采用 RED→GREEN 测试驱动，至少覆盖：

### Backend 与 Gateway 边界

- 每次新登录会话缺少 phone code 都失败；
- 新手机号创建持久 pending 用户并签发未认可令牌；
- 未认可令牌的 issuer、audience、use、version 和正式令牌严格分离；
- 每个服务端登录结果在手机号解析后写入含手机号的事件；临时 code/JWT 不落库；
- 手机号/openid 冲突、禁用、并发登录和限流；
- 学生/老师申请字段、年级反算、两手机号不同与登录手机号匹配；
- 同学生最多两身份、跨学生手机号冲突、另一手机号待绑定；
- 普通管理员审核边界与超级管理员高权限边界；
- `submitted → provisioning → approved/rejected` 状态机；
- 会员共享、迁移和只在正式身份返回；
- 未认可路由白名单、真实 API 直连拒绝、空数据和缓存隔离；
- 固定示例题、Word/PDF、过期、取消、跨会话拒绝和请求上限。
- 小程序所有认证、申请、会员和正式/体验 API 都命中 `/scheduling` Backend；Gateway 不读取或镜像身份表；
- 旧体验码、`review-demo` 和合成角色入口返回 410，旧审核令牌对两侧均无效。

### 本地数据主机

- 学生新增字段及旧数据库向前迁移；
- 入学年份复核、学校自动维护和 parent/student 跨字段手机号唯一检查；
- 学生/老师无匹配创建、兼容匹配复用、冲突拒绝；
- provisioning receipt 幂等、重复 claim、进程重启和重复完成；
- 老师创建不写课时费；
- 任务结果只返回最小实体映射。

### 小程序

- 登录页没有体验码或角色选择，手机号按钮为唯一入口；
- 未认可学生导航、体验标记、正式业务空态和示例题标记；
- 学生/家长与老师表单的必填/选填规则；
- 所有申请状态、拒绝重提、主机处理中和通过后重新登录；
- 学生、家长、老师、管理员正式导航和数据范围；
- 会员标记只出现在账号名称旁；
- 身份切换清空真实业务、权限、任务和下载缓存；
- 网络、离线、403、401、限流和冲突文案。

### 全页面与运行时

必须维护 `miniapp/src/app.config.ts` 全部 16 个注册页面清单，并为适用角色和关键状态留下真实微信运行时截图或检查记录：未认可学生、受认可学生、家长登录、老师、普通管理员、超级管理员，以及空态、离线、无权限、有限写入、申请各状态。`miniappUiCoverage` 必须通过，首页截图不能代表整套 UI。

## 兼容发布与回滚

所有数据库迁移采用新增表、列、索引和可重复执行的向前迁移，不删除旧字段。部署前分别备份阿里云 Backend/Gateway 和本地权威数据库。

现有账号迁移规则：

- 已批准且具有有效 `student_id` 的学生身份创建 `subject_type=student` 的会员记录；同一学生的现有学生/家长身份只能共享该记录；
- 已批准且具有有效 `teacher_id` 的老师身份创建 `subject_type=teacher` 的会员记录；
- 现有管理员和固定超级管理员创建 `subject_type=user` 的会员记录；
- 已批准学生/老师若缺少有效业务实体映射，标记为 `manual_resolution_required`，不得仅凭旧 `review_status` 自动开通；
- 现有未批准真实用户保持 pending，并在下次强制手机号验证后进入未认可学生体验态；
- 旧合成审核用户不迁移为正式身份，旧审核会话、体验码和令牌全部失效，相关入口返回 410。

发布顺序：

1. 先部署兼容的 Backend 数据库、单一认证/申请服务、体验沙箱和路由，再部署 Gateway 410 tombstone 与边界拒绝；正式旧用户登录保持可用。
2. 升级指定本地数据主机，验证新任务协议、学生家长字段、题库盘和同步链路。
3. 验证主机心跳声明 provisioning 能力后才开放管理员批准按钮。
4. 构建并上传新小程序，逐页运行时验证。
5. 构建并发布 OSS 桌面更新，恢复 Node ABI 并验证更新 feed。
6. 执行阿里云内外网健康、权限契约和未认可直连绕过探针。
7. 提交微信审核/发布并记录平台结果。

回滚只回滚代码和功能开关，不删除已经创建的学生、老师、认证身份、会员或审计记录。若新申请流程需关闭，服务端停止新提交/批准，但保持已认可用户正式登录；绝不恢复体验码或放宽未认可权限。若任一端未完成、版本不一致或微信平台阻断，只能报告“部分发布”或“受阻”。
