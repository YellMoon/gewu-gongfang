# 小程序手动手机号登录设计

## 背景与目标

当前小程序登录依赖微信 `getPhoneNumber` 能力。现阶段主体条件无法取得该能力，导致登录入口不可用。

本次改造将登录入口调整为用户手动填写中国大陆手机号，并继续使用 `Taro.login()` 获取当前小程序账号的微信 `openid`。改造后保留现有正式账号、未识别用户体验、正式账号申请、管理员审核、权限签发和审计流程。

手填手机号只是身份申报，不是手机号所有权证明。系统不得因为用户知道某个正式账号的手机号，就直接把该正式身份授予一个新的微信账号。

## 范围

本次包含：

- 小程序登录页的手机号输入、校验、状态提示和隐私文案。
- Backend 登录接口对手填手机号和旧版微信手机号授权的兼容。
- 手填手机号登录的微信绑定规则。
- 正式身份绑定申请的存储、管理员查看、批准、拒绝和审计。
- 管理员用户权限页中的微信绑定待审核状态。
- 登录、刷新、退出和审核后的重新登录行为。
- 数据库迁移、接口契约、测试、小程序构建上传和统一版本发布。

本次不包含：

- 短信验证码服务。
- 微信小程序主体迁移或 `getPhoneNumber` 权限申请。
- 桌面端设备身份确认流程的手机号获取方式变更。
- 自动替换一个已绑定正式账号的微信 `openid`。

## 方案选择

采用“手填手机号 + 微信 openid + 高权限身份首次绑定需管理员审核”方案。

未采用的方案：

- 短信验证码：安全性好，但需要短信供应商、费用、模板审核和新的运维配置。
- 仅凭手机号直接登录：实现简单，但任何知道他人手机号的人都可能冒充，不能接受。

## 登录状态机

### 1. 已绑定微信账号

系统先按 `openid` 查找账号。

- 输入手机号与该账号 `phone_normalized` 一致：按原有规则签发正式或未识别用户会话。
- 输入手机号不一致：返回 `OPENID_PHONE_BINDING_CONFLICT`，不修改任何绑定。
- 账号已停用、删除或正式身份映射无效：继续使用现有拒绝规则。

### 2. 新微信账号 + 全新手机号

如果 `openid` 和手机号均不存在：

- 创建未识别用户。
- 绑定当前 `openid` 和手填手机号。
- 签发未识别用户会话。
- 用户继续使用现有体验功能，并可提交正式账号申请。

该路径不会获得正式业务权限。

### 3. 新微信账号 + 已存在但未绑定微信的账号

如果手机号已属于现有账号、但账号没有 `wechat_openid`：

- 不直接绑定。
- 创建或复用一条待审核微信绑定申请。
- 返回 `WECHAT_BINDING_REVIEW_REQUIRED`，不签发该现有账号的会话。
- 管理员批准后，以事务方式写入 `wechat_openid`/`wechat_unionid`、递增 `auth_version`、完成申请并写审计。
- 用户重新登录后，才获得与该账号当前审核状态匹配的会话。

该规则适用于正式账号，也适用于已经存在的未识别账号，避免已有申请资料被他人接管。

### 4. 手机号已绑定其他微信账号

如果手机号所属账号已有不同的 `wechat_openid`：

- 返回 `PHONE_WECHAT_BINDING_CONFLICT`。
- 不自动解绑、不创建可自动批准的替换申请。
- 界面提示联系管理员处理微信换绑。
- 管理员必须先通过明确的换绑管理操作撤销旧绑定；本次功能不新增自动换绑能力。

### 5. 旧版微信手机号授权兼容

Backend `/api/auth/wechat-login` 在过渡期同时接受：

- 新版：`{ code, phone }`
- 旧版：`{ code, phoneCode }`

`phoneCode` 路径仍由服务器向微信换取已验证手机号，并沿用原有可信手机号登录规则。`phone` 路径必须进入本设计的新规则，二者不得共用会自动绑定正式账号的实现。

如果请求同时携带 `phone` 和 `phoneCode`，服务器优先验证 `phoneCode`，并要求换取的手机号与手填手机号一致；不一致时拒绝登录。

## 数据模型

新增 `miniapp_wechat_binding_requests`：

- `id`
- `target_user_id`
- `phone_normalized`
- `candidate_openid`
- `candidate_unionid`
- `status`：`submitted`、`approved`、`rejected`、`expired`
- `revision`
- `reviewed_by`
- `review_note`
- `created_at`
- `updated_at`
- `resolved_at`

约束：

- 同一 `candidate_openid` 同时只能存在一条 `submitted` 申请。
- 同一目标用户同时只能存在一条 `submitted` 申请。
- 创建、复用、批准、拒绝均在事务内完成。
- 批准时重新检查目标账号、手机号和 openid 冲突，不能只依赖申请创建时的状态。
- 管理员重复提交相同批准/拒绝操作时必须幂等；`revision` 不一致时返回冲突。
- 绑定申请纳入隐私保留与脱敏策略。

现有 `miniapp_login_events` 继续记录登录结果。绑定申请表负责保存申请人 openid 和审核轨迹；不把未确认的新 openid 提前写入 `users`。

## 接口契约

### `POST /api/auth/wechat-login`

新版请求：

```json
{
  "code": "wx-login-code",
  "phone": "13800138000",
  "miniappVersion": "6.3.3",
  "platform": "wechat"
}
```

成功响应保持现有 `{ success, data: { token, user } }` 契约。

待审核响应使用 HTTP 202：

```json
{
  "success": false,
  "code": "WECHAT_BINDING_REVIEW_REQUIRED",
  "data": {
    "requestId": "binding-request-id",
    "status": "submitted"
  }
}
```

其他新增或明确化错误：

- `MANUAL_PHONE_REQUIRED`
- `MANUAL_PHONE_INVALID`
- `OPENID_PHONE_BINDING_CONFLICT`
- `PHONE_WECHAT_BINDING_CONFLICT`
- `WECHAT_PHONE_MISMATCH`
- `WECHAT_BINDING_REVIEW_REQUIRED`

接口继续执行 IP 限流，不在响应中暴露“该手机号是否为超级管理员”等敏感信息。

### 管理员接口

在现有管理员权限路由下增加：

- 查询待审核微信绑定申请。
- 批准指定申请，必须提交 `expectedRevision`。
- 拒绝指定申请，必须提交 `expectedRevision`，拒绝原因可选。

仅超级管理员可批准或拒绝微信绑定申请；普通管理员只读，保持现有高风险权限边界。

## 小程序界面

登录页：

- 移除 `openType="getPhoneNumber"`。
- 增加手机号输入框，使用数字键盘，最多 11 位。
- 按钮改为“登录并验证身份”。
- 文案明确说明：手机号用于匹配账号；首次绑定正式账号可能需要管理员审核。
- 本地只保留本次输入所需状态，不持久化明文手机号。
- 提交时仍先调用 `Taro.login()` 获取一次性 code。

状态提示：

- 待审核：提示“微信账号绑定申请已提交，管理员确认后请重新登录”。
- 手机号或微信冲突：提示联系管理员，不暗示用户反复尝试其他手机号。
- 网络失败和限流：沿用现有错误边界。

正式账号申请页：

- 将“微信已验证手机号”改为“登录时填写的手机号”。
- 该字段来自当前会话、不可在申请页修改。
- 明确管理员会核对申请资料和手机号。

管理员用户权限页：

- 增加“微信绑定待审核”分组及数量。
- 展示脱敏手机号、目标账号、申请时间和状态。
- 批准前二次确认将绑定到哪个账号。
- 普通管理员看得到但不能操作；超级管理员可以批准或拒绝。

页面清单和 UI 覆盖记录必须同步更新，不再把登录页标记为 `verified-phone-binding` 或 `Button(open-type=getPhoneNumber)`。

## 安全与隐私

- 手填手机号永远不标记为“微信已验证”。
- 正式账号的新 openid 绑定必须经过管理员审核。
- 审核批准后递增用户 `auth_version`，使旧会话失效。
- 登录接口限流、冲突审计、申请审核审计继续生效。
- 日志不得记录微信登录 code、phoneCode、JWT 或完整请求体。
- 管理员列表默认展示脱敏手机号；服务端仍以规范化手机号完成匹配。
- 绑定申请按现有小程序隐私保留周期清理或脱敏。

## 兼容与发布顺序

为避免多端版本窗口导致登录中断：

1. 先部署兼容新旧请求的 Backend 和数据库迁移。
2. 验证旧版 `phoneCode` 契约仍可用，且手填手机号路径不会绕过审核。
3. 构建并上传新版小程序。
4. 核验微信开发者平台上传版本和页面清单。
5. 桌面端、数据主机和 OSS 更新按统一版本矩阵继续发布。

如果微信平台阻止上传或发布，整体状态必须标记为“部分发布”或“受阻”，不能宣称全部完成。

## 测试与验收

Backend 至少覆盖：

- 已绑定 openid + 匹配手机号成功。
- 已绑定 openid + 不匹配手机号拒绝。
- 全新 openid + 全新手机号获得未识别会话。
- 全新 openid + 已存在未绑定手机号生成待审核申请，不获得会话。
- 同一申请重复登录不会生成多条活动申请。
- 手机号已绑定其他 openid 时拒绝。
- 超级管理员批准后能够重新登录。
- 普通管理员不能批准或拒绝。
- 批准时出现并发绑定冲突会回滚。
- 旧版 `phoneCode` 路径保持兼容。
- 同时提交 `phone`/`phoneCode` 且号码不一致时拒绝。
- 登录事件、绑定审计和隐私脱敏正确。

小程序至少覆盖：

- 手机号为空、格式错误、输入长度和按钮忙碌状态。
- 成功登录、待审核、绑定冲突、网络失败、限流提示。
- 登录提交不再依赖 `getPhoneNumber`。
- 账号申请页和隐私文案不再声称手机号经过微信验证。
- 全页面 UI 覆盖检查通过。

最终验收：

- 相关单测、完整 `npm test`、类型检查、前端和小程序构建通过。
- 阿里云部署前完成数据库与代码备份，部署后健康检查和登录契约检查通过。
- 小程序完成真实上传并记录版本证据；若平台阻断则如实记录。
- 此前桌面端、数据主机、OSS 更新和夸克交付任务继续按既定清单完成。
